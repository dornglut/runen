# A0 Verification Contract

Status: **non-normative conformance-oracle documentation**

This document owns the test obligations for the executable A0 oracle. The normative semantics exercised by A0 are owned by `spec/language/core/value-storage.md`, `spec/language/core/borrowing.md`, `spec/language/core/pointers.md`, `spec/language/core/unsafe.md`, and `spec/language/core/functions.md`.

## Core MIR validation boundary

Raw `runen-core-ir::Body` is a construction/data form. It is not executable by the reference machine until `validate_body` establishes the structural and language-validity rules represented by the current A0 MIR and returns `ValidatedBody`. This is language validation, not the environment-admission phase defined by `spec/language/lifecycle.md`.

Validation rejects unknown identifiers and types, recursive by-value type graphs unsupported by the current structural representation, invalid block targets and direct/loan-relative place projections, operand/value type mismatch, `Copy` of a non-copy type, ordinary assignment to an immutable containing local, `InteriorAssign` whose resolved target is outside an interior-mutable region, `AddressOf` whose destination raw-pointer pointee type does not match the selected source type, and `RawRead`/`RawMove`/`RawAssign` whose selected pointer-value place does not have a raw-pointer type. `RawMove` produces exactly the selected raw-pointer pointee type, and `RawAssign` requires its source type to equal that pointee type. Raw-pointer pointee edges are semantic indirection rather than structural containment, so they do not make an otherwise finite structural type recursively invalid.

Validation also proves reachable initialization and active-loan-forest state transitions for defined executions. `Init` requires a wholly vacant selected destination, meaning every recursively contained scalar leaf is Never-initialized or Dead, and retains ordinary exclusive direct-storage authority. That vacancy is established before source operand state transitions, so source evaluation cannot manufacture vacancy for the same `Init`. Result-bearing direct calls use the same wholly-vacant and Init-like exclusive destination admission before argument state transitions. Ordinary reads, moves, and copies require fully initialized storage; explicit `Drop` requires at least one Live subobject; every root borrow or reborrow requires a fully Live selected target and compatible current authority. `InteriorAssign` requires shared alias authority plus an independently marked interior-mutable target. `AddressOf` requires shared alias authority but does not require the selected stored value to be Live because it selects existing storage without reading the pointee value. `RawRead`, `RawMove`, and `RawAssign` require the **pointer value itself** to be fully Live and readable with ordinary shared `PlaceAccess` authority.

Defined `RawAssign` and `RawMove` each change initialization/value state at an indirectly selected target. The validator therefore carries one exact static `Place` target inside every Live raw-pointer leaf. This metadata is derived only from currently represented `AddressOf` and pointer-value transport. It is verification path-state, not an independent provenance identifier, address, loan authority, or Runen-observable value.

Exact pointer-target metadata follows ordinary value semantics:

- `AddressOf` records the resolved concrete source place;
- pointer `Copy` duplicates that target metadata;
- ordinary pointer `Move` transfers it while ending the source pointer stored-value lifetime;
- defined `RawMove` of pointer-valued target storage transfers the same metadata through the ordinary Move lifecycle;
- aggregate Copy/Move recursively transports targets in raw-pointer leaves;
- writes install source pointer metadata in the written raw-pointer leaves;
- replacement and destruction remove metadata belonging to ended pointer stored-value lifetimes.

Because exact pointer targets can affect later `RawAssign` and `RawMove` storage transitions, they participate in validation loop-state repetition together with ordinary storage and active-loan-forest state.

Exact target knowledge does **not** reclassify raw-target unsafe obligations as MIR-validity rules. A `ValidatedBody` may contain a `RawRead` whose target is not Live or conflicts with an exclusive loan, a `RawMove` whose target is not fully Live or conflicts with any active overlapping loan, or a `RawAssign` whose target conflicts with an active shared or exclusive loan. Those remain execution-time unsafe proof obligations under their normative owners.

Path-state validation models only defined execution continuations. Static structural/type validation still examines the complete body first. When exact verification state proves that a represented raw operation's unsafe target precondition fails, path-state validation therefore:

- emits no MIR-validation diagnostic for that unsafe failure;
- does not fabricate a post-UB storage state or owned operand result;
- stops path-state propagation for that deterministic execution path because there is no defined Core continuation after the violation.

The reference machine still checks the unsafe precondition during execution and reports detected UB through `UndefinedBehavior`; validator knowledge is not an observable safety result and does not remove the runtime oracle check. For `RawAssign`, its target is snapshotted before source evaluation, source evaluation occurs first, and a failing `RawMove` source prevents any defined outer replacement. If source evaluation is defined but the outer target compatibility check fails, no replacement post-state is propagated.

The reference machine accepts only `ValidatedBody`. Its execution API therefore has no malformed-MIR or language-invalid-MIR result. Execution either produces a defined `ExecutionReport`, enters detected undefined behavior through the verification-only `UndefinedBehavior` channel, or may diverge. A represented `Terminator::Fault` is a defined terminal execution, not a validation error or UB report, and performs the cleanup required by the normative value/storage semantics after the complete active loan forest ends. Detected UB does not fabricate defined Return/Fault cleanup.

## Lifetime and destruction-domain coverage

The oracle uses the normative distinction between storage extent and stored-value lifetime. Existing `NeverInitialized`, `Live`, and `Dead` state is sufficient for the current stored-value lifecycle; this verification layer does not invent stored-value lifetime IDs or numeric addresses.

Tests must distinguish at least these consequences:

- the same storage may remain in extent while successive stored-value lifetimes begin and end;
- move ends source stored-value lifetime without destruction;
- defined `RawMove` reuses that same ownership-transfer lifecycle at an indirect target, leaving the complete target Dead and yielding the moved value without source destruction;
- move or explicit destruction leaves Dead storage, and `Init` may begin a later stored-value lifetime when the selected destination is wholly vacant;
- vacant `Init` is non-replacing, requires no ordinary local assignment mutability, and performs no destination destruction;
- mutable `Assign` may begin a new stored-value lifetime after move or destruction;
- ordinary, interior, and raw-pointer replacement evaluate their source before determining and destroying the destination's current destruction domain;
- interior replacement may occur without ordinary local assignment mutability when the destination is independently marked interior-mutable and the borrowing requirement is satisfied;
- unsafe `RawAssign` does not require ordinary local assignment mutability or an interior-mutability marker because its target-write gate is separately defined;
- unsafe `RawMove` likewise does not derive target permission from those mutation capabilities; it uses its own unsafe target ownership-transfer preconditions;
- explicit drop and termination cleanup destroy only the then-Live destruction domain and never repeat destruction of moved or already-destroyed leaves;
- defined `Fault` uses the same current-domain cleanup rule as defined `Return`;
- a successful non-consuming `RawRead` does not end the pointee's stored-value lifetime or alter its initialization state;
- a successful `RawMove` ends the complete pointee stored-value lifetime without destruction and leaves target storage Dead;
- a successful `RawAssign` may initialize Never-initialized storage, replace partial/Live storage, or reinitialize Dead storage and leaves the complete target Live.

Verification events expose enough ordering to prove these rules where the synthetic tracked fixture is used, but those events remain non-observable oracle instrumentation.

## Dynamic storage identity and raw-pointer formation coverage

The reference machine creates one verification representation of dynamic storage-instance identity for each local storage extent in an execution. That identity remains stable for the extent and is distinct from static `LocalId`, stored-value lifetime, pointer provenance, and physical or numeric address semantics.

`Operand::AddressOf` forms a non-null raw-pointer runtime value by selecting one symbolic `StorageRegion`: the target local's dynamic storage-instance identity plus its structural projection path. The currently defined provenance fact is only that the pointer's provenance is rooted in the target dynamic storage instance. The oracle therefore stores the symbolic target once; `target.instance` is sufficient verification evidence for that provenance root and is not a separately observable provenance token.

The validator's exact static `Place` target and the oracle's dynamic `StorageRegion` target are two verification representations of the same already normative target relationship at different stages. The validator representation exists because defined RawAssign and RawMove effects must update later path-state; it does not add provenance semantics.

Validation and execution must prove at least:

- distinct simultaneously existing local storage extents receive distinct dynamic storage-instance identities;
- one continuing local storage extent keeps the same identity across initialization, including later vacant `Init`, ordinary or raw move, explicit destruction, ordinary replacement, interior replacement, and raw-pointer replacement;
- structural projections in pointer targets are semantic paths rather than byte offsets or layout facts;
- direct and loan-relative `AddressOf` selecting the same concrete storage produce the same currently defined symbolic target/provenance-root metadata;
- pointer formation may select Never-initialized or Dead storage while its storage extent continues;
- ending or reusing the loan that authorized formation does not mutate an already formed raw-pointer value;
- ordinary raw-pointer `Copy`, ordinary `Move`, defined `RawMove`, storage, replacement, and destruction preserve or consume the raw-pointer value according to ordinary value/storage rules while preserving its defined pointer metadata where the value continues.

Raw-pointer mutation beyond `RawAssign`, a general dereference-place abstraction, non-consuming owned raw-copy loads, byte-wise raw loads or writes, pointer arithmetic, numeric-address conversion, complete provenance structure or invalidation, relocation or pinning, pointer equality/ordering/hashing, null semantics, value-representation validity, dangling access outside the currently represented local-storage model, and complete undefined-behavior closure remain outside this verification contract.

## Raw-pointer read and unsafe-access coverage

`Statement::RawRead { pointer: PlaceAccess }` is the non-consuming raw-pointer target-read operation. It reads the current pointee and discards the semantic result. It does not create a dereferenced place, duplicate or move an owned pointee value, mutate the target, or alter the raw pointer.

The validator and reference machine deliberately divide responsibility at the accepted semantic boundary:

- validation proves that `pointer` selects a raw-pointer-typed, fully Live pointer value and that the pointer-value storage is readable through ordinary shared `PlaceAccess` authority;
- execution resolves that pointer value's symbolic `StorageRegion` back to the current structural place by matching dynamic storage-instance identity rather than interpreting the numeric identity as a `LocalId`;
- the target must be fully Live at the access;
- an active shared loan overlapping the target is compatible with the raw read;
- an active exclusive loan overlapping the target violates the raw target shared-access precondition;
- disjoint active loans do not constrain the target read.

The pointer does not retain the loan that authorized `AddressOf`. Target compatibility is evaluated against the active loan state at the `RawRead` step itself.

The currently represented target-liveness and target-loan compatibility obligations are unsafe preconditions. Violation is undefined behavior under the normative unsafe contract, not malformed MIR, a validation failure, defined `Fault`, or recoverable application failure. Exact validator state may establish that there is no defined path-state continuation after such a violation without converting that fact into a validation diagnostic.

Tests must prove at least:

- a live raw pointer can read a fully Live target;
- the read is non-consuming even when the pointee type is the synthetic non-copy tracked fixture;
- an uninitialized or moved pointer **value** is rejected at MIR validation;
- a non-pointer `RawRead` operand is rejected at MIR validation;
- a shared loan may supply the pointer-value `PlaceAccess` for `RawRead` without upgrading its authority;
- an exclusive loan over the pointer-value storage blocks `RawRead` at MIR validation;
- a pointer formed to Never-initialized target storage is language-valid but `RawRead` while that target remains Never-initialized is detected UB;
- a pointer whose target becomes Dead after move or explicit destruction cannot be raw-read while Dead;
- legal replacement in the same continuing storage makes a previously formed pointer readable again without changing its symbolic target/provenance root;
- ordinary, interior, and raw-pointer replacement preserve the continuing target storage identity used by a later successful `RawRead`;
- whole-aggregate `RawRead` requires the complete target to be Live, not merely one initialized field;
- overlapping shared target loans permit the raw read;
- an overlapping exclusive target loan is detected UB;
- a disjoint active loan, including an exclusive sibling-field loan, does not constrain the raw read;
- ending the source loan used for pointer formation does not revoke a later raw read when the current target preconditions hold;
- a successful raw read may still be followed by a defined `Fault` with normal cleanup;
- a detected UB path does not perform defined termination cleanup.

## Raw-pointer ownership-move and unsafe-access coverage

`Operand::RawMove(pointer: PlaceAccess)` is the ownership-producing raw-pointer target operation. It snapshots the stored pointer's target, and when target liveness and exclusive-access preconditions hold, reuses the ordinary Move lifecycle at that target and yields the moved pointee value to its enclosing operation.

Validation proves only the explicit language-validity and defined path-state facts:

- `pointer` has raw-pointer type, is fully Live, and is obtained through ordinary shared `PlaceAccess` authority;
- the operand's produced type is exactly the pointer pointee type;
- exact pointer-target metadata is propagated through ordinary value transport and through defined RawMove of pointer-valued target storage;
- after a defined RawMove, the complete exact target is Dead and the moved `ValidationValue` is available to the enclosing operation.

Validation deliberately does **not** turn raw target liveness or compatibility into MIR diagnostics. When exact state proves either precondition fails, path-state propagation ends without fabricating a moved value. Execution independently checks:

- the complete target must be fully Live;
- any overlapping shared loan violates the raw target exclusive-access precondition;
- any overlapping exclusive loan violates it;
- disjoint active loans do not constrain RawMove.

A failure is detected UB, not malformed MIR, language-invalid MIR, a defined `Fault`, or a recoverable result. The enclosing operation performs no defined destination destruction or write after a failing RawMove operand.

Tests must prove at least:

- non-pointer RawMove and enclosing result-type mismatch are MIR validation errors;
- uninitialized/dead/moved pointer-value access remains a MIR validation error;
- shared loan-relative pointer-value access is valid without granting target authority;
- an exclusive loan over pointer-value storage blocks RawMove pointer access at MIR validation;
- a defined RawMove of a fully Live target leaves the exact target Dead for later safe validation;
- moving a tracked pointee performs no destruction at the source and the moved value is destroyed exactly once later at its destination;
- whole-aggregate RawMove requires every target leaf Live;
- pointer-valued pointee movement preserves exact target/provenance metadata;
- self-targeting RawMove snapshots pointer target selection before moving the same pointer storage;
- Never-initialized, Dead, and partial whole-target cases are detected UB rather than validation failures;
- overlapping shared and exclusive target loans each produce detected UB;
- disjoint active loans do not block the ownership transfer;
- ending the pointer-formation loan neither grants nor revokes later RawMove by itself;
- ordinary local assignment mutability and interior-mutability markers are not RawMove target permissions;
- `Assign(dst, RawMove(ptr_to_dst))` remains source-first and does not double-destroy the moved value;
- a failing RawMove source prevents an enclosing RawAssign write;
- exact statically evident raw UB stops path-state propagation without suppressing whole-body static/type validation;
- successful RawMove may be followed by defined `Fault` with normal cleanup;
- detected RawMove UB performs no defined Return/Fault cleanup.

## Raw-pointer replacement and unsafe-access coverage

`Statement::RawAssign { pointer: PlaceAccess, src: Operand }` is the source-first semantic raw-pointer replacement operation. It snapshots the stored pointer's target before source evaluation and then, when the raw target exclusive-access precondition holds, applies the existing replacement lifecycle to that target.

Validation proves only the explicit language-validity and defined path-state facts:

- `pointer` has raw-pointer type, is fully Live, and is obtained through ordinary shared `PlaceAccess` authority;
- `src` has the pointer pointee type and obeys ordinary operand legality, including the unsafe target preconditions of a RawMove source when present;
- exact pointer-target metadata is propagated through represented pointer-value transport;
- after a defined RawAssign step, the exact target path-state reflects the source-first replacement result and is fully Live.

Validation deliberately does **not** turn raw target compatibility into a borrow diagnostic. Execution checks the current target against all active concrete loans after source evaluation:

- any overlapping shared loan violates the raw target exclusive-access precondition;
- any overlapping exclusive loan violates it;
- disjoint active loans do not constrain RawAssign.

A conflict is detected UB, not malformed MIR, language-invalid MIR, a defined `Fault`, or a recoverable result. Source evaluation events and state that occur before detected outer UB remain verification evidence, while defined replacement and Return/Fault cleanup do not occur after the violation. If source evaluation itself enters UB, including through RawMove, no source value or outer RawAssign write is fabricated.

Tests must prove at least:

- Live target replacement destroys the old destruction domain exactly once before the RawAssign write and normal cleanup later destroys the replacement exactly once;
- Never-initialized and Dead targets can be made Live by defined RawAssign;
- partial aggregate replacement destroys only then-Live old leaves and leaves the whole target Live;
- non-pointer, uninitialized/dead pointer-value, pointer-storage authority, and source-type failures remain MIR validation errors;
- shared loan-relative pointer-value access is valid without granting target authority;
- exact target metadata survives direct pointer Copy/Move, RawMove of pointer-valued storage, nested aggregate transport, pointer replacement, and destruction/reinitialization under ordinary value rules;
- defined RawAssign updates exact validator target path-state so later safe read/move/borrow validation sees the target as Live;
- target selection is snapshotted before source evaluation;
- source evaluation precedes target destruction, including moving from the selected target and writing the moved value back without double destruction;
- a RawMove source may update its own target state before the outer RawAssign check, and RawMove-source UB prevents the outer write;
- successful RawAssign does not retroactively change the snapshotted target even when pointer/source/target storage overlap under otherwise legal semantics;
- overlapping shared and overlapping exclusive target loans each produce detected UB;
- disjoint shared/exclusive loans do not block the target write;
- ending the pointer-formation loan neither grants nor revokes later RawAssign by itself;
- immutable and non-interior-marked target storage can be replaced by RawAssign when its unsafe target-write precondition holds;
- successful RawAssign may be followed by defined `Fault` with normal cleanup;
- detected RawAssign UB performs no defined Return/Fault cleanup.

## Borrow and access coverage

Borrow intervals are separate from storage extent and stored-value lifetime.

`Body::loans` declares typed semantic loan identities. A declaration may be activated for multiple sequential borrow intervals, but it cannot be activated twice concurrently. `Statement::Borrow` takes a `PlaceAccess`: a direct source creates a root interval, while an active-loan source creates a child interval. Each dynamic activation receives fresh concrete-root and parent state.

`PlaceAccess::Direct` reaches storage through its local place. `PlaceAccess::Loan` reaches an active loan root plus relative structural projections. Neither representation is a pointer value, physical address, provenance token, stored reference, or frozen source-language reference syntax. `RawRead`, `RawMove`, and `RawAssign` use `PlaceAccess` only to reach their stored pointer value; the pointee target remains a symbolic raw-pointer target rather than a new `PlaceAccess` form.

Validation and execution must prove at least:

- place overlap is structural and address-independent: roots overlap descendants while sibling fields are disjoint;
- overlapping shared root loans may coexist;
- an exclusive root loan conflicts with every overlapping active loan;
- exclusivity and assignment mutability remain separate: immutable storage may participate in exclusive root borrowing and exclusive reborrowing while ordinary assignment remains illegal;
- shared loans permit `Read`, copyable `Copy`, `AddressOf`, pointer-value access for `RawRead`/`RawMove`/`RawAssign`, shared reborrow creation, and `InteriorAssign` only when the independently resolved target lies within an interior-mutable region;
- shared loans do not permit ordinary `Move`, ordinary `Assign`, `Drop`, or exclusive reborrow;
- exclusive loans include shared authority and additionally permit ordinary `Move`, `Drop`, exclusive reborrow, and ordinary `Assign` when containing-local assignment mutability permits it; their included shared authority also permits pointer-value access for `RawRead`/`RawMove`/`RawAssign`;
- direct reads, copies, `AddressOf`, pointer-value access for `RawRead`/`RawMove`/`RawAssign`, and legal `InteriorAssign` may coexist with overlapping shared loans, while direct exclusive-authority operations may not;
- any overlapping exclusive loan blocks direct shared or exclusive `PlaceAccess`;
- shared children may be created from shared or exclusive parents that retain shared authority;
- exclusive children may be created only from exclusive parents that retain exclusive authority;
- a child borrow delegates only its concrete overlapping region; disjoint parent sub-places retain their prior authority;
- an overlapping exclusive child completely suspends direct-parent access to that region;
- an overlapping shared child leaves shared authority on that region, including `Read`, copyable `Copy`, `AddressOf`, pointer-value access for `RawRead`/`RawMove`/`RawAssign`, shared reborrow, and eligible `InteriorAssign`, while blocking exclusive-authority operations;
- only direct children are required to compute a parent's retained authority because deeper descendants cannot return authority to the grandparent while their direct ancestor remains active;
- explicit parent end is rejected while a child remains active, so nested intervals end leaf-to-root;
- ending a child restores the direct parent's prior authority subject to any other active direct children;
- active loan declarations form a forest and an active declaration cannot be reused to create a cycle;
- reusing an inactive `LoanId` creates a fresh interval without stale parentage;
- exclusive access controls storage rather than one stored-value lifetime, so ordinary move/drop followed by ordinary assignment through the same active exclusive root or child loan is legal for mutable storage when ordinary value/storage rules permit it;
- shared loans may remain active across legal interior replacement because the loan governs the continuing structural storage region rather than one immutable stored-value lifetime;
- active-loan forest state participates in loop-state repetition;
- defined `Return` and defined `Fault` end the complete active loan forest before cleanup;
- raw target-read, raw target-move, and raw target-write compatibility are checked against current active concrete loan kind/root state without treating a raw pointer as stored loan authority.

Source lifetime parameters or inference, first-class reference values, source-level interior-mutability APIs or runtime borrow guards, raw-pointer operations beyond the represented RawRead/RawMove/RawAssign forms, general dereference places, complete provenance semantics, relocation or pinning, allocation/deallocation, value-representation validity, the complete undefined-behavior taxonomy, source `unsafe`, and concurrency/memory-ordering semantics remain outside this verification contract.

## Required cases

The A0 suite covers at least:

- move invalidates the source, with a later use rejected by MIR validation;
- copy preserves the source;
- partial move preserves disjoint live sub-places and makes the aggregate unreadable as a whole;
- independently initialized fields can form a fully initialized aggregate;
- non-copy values cannot be copied;
- `Init` can begin a later stored-value lifetime in Dead storage after move or explicit destruction without ordinary assignment mutability or replacement destruction;
- `Init` admits a wholly vacant aggregate containing any mixture of Never-initialized and Dead leaves, rejects a selected destination containing any Live leaf, and checks only the selected projected sub-place;
- zero-leaf structural `Init` is vacuously vacant and introduces no hidden aggregate lifetime state;
- `Init` vacancy is checked before source operand transitions, so `Init(dst, Move(dst))` cannot replace a Live value;
- cyclic validation may revisit the same `Init` after the prior stored-value lifetime ended, while a backedge that reaches the same `Init` with Live destination storage remains invalid;

- mutable `Assign` can initialize Never-initialized storage;

- mutable `Assign` can replace partially initialized aggregate storage while destroying only live old subobjects;

- moved or already-dropped values are not destroyed twice;
- field and local cleanup order matches the normative value/storage semantics;
- defined fault cleanup uses the then-current destruction domain and destroys each remaining live value exactly once;
- structural root/field overlap and sibling disjointness;
- overlapping shared root loans, conflicting exclusive root loans, and disjoint exclusive field loans;
- direct-versus-loan permission cases for shared and exclusive borrowing;
- shared child from shared parent and shared child from exclusive parent;

- distinct local storage extents have distinct pointer-provenance roots in the current storage-rooted model;
- field `AddressOf` records a structural target path without layout semantics;

- pointer formation before and after ordinary, interior, or raw replacement preserves the continuing storage identity and currently defined pointer metadata where pointer storage itself continues unchanged;
- ordinary move, RawMove, and explicit drop end stored-value lifetimes without changing the continuing target storage identity;
- raw-pointer copy, ordinary move, and RawMove preserve the defined symbolic pointer metadata when they transport a pointer value;
- ending the source loan does not mutate a previously formed raw pointer;
- shared-child, exclusive-child, disjoint-child, inactive-loan, and Dead-storage cases enforce the accepted alias-authority rules for `AddressOf`;
- `RawRead` distinguishes pointer-value validation failures from pointee-target UB;
- shared loan-relative pointer-value access for `RawRead` is valid and executes through the same stored raw-pointer value;

- Never-initialized, Dead, and partially initialized raw targets violate the RawRead unsafe target precondition;
- replacement in continuing storage can make an existing raw-pointer target readable again;

## Semantic and verification-only constructs

`Statement::Read`, `Statement::Borrow`, `Statement::EndBorrow`, `Statement::InteriorAssign`, `Statement::RawRead`, and `Statement::RawAssign` represent semantic Core operations in the current proving MIR. `Operand::RawMove` is likewise an unsafe semantic owned-value operation. `RawRead`, `RawMove`, and `RawAssign` have unsafe target preconditions normatively owned by the pointer, borrowing, and unsafe specifications. `Operand::AddressOf` represents the currently defined raw-pointer formation operation. `PlaceAccess` records whether an ordinary MIR operation reaches storage directly or relative to an active loan. These MIR forms do not claim source-language syntax, runtime reference representation, stored reference identity, or a general dereference-place model.

`StorageInstanceId` and `StorageRegion` are proving/oracle representations of the accepted dynamic storage identity and structural-region semantics. Their numeric identity representation and structural projection data are not physical addresses, byte offsets, ABI layout, or Runen-observable values.

`runen-reference::RawPointerValue` is the oracle's private runtime representation of one currently defined raw-pointer value. Its symbolic `target` is the single stored source of truth for the accepted pointer target and provenance root; the oracle does not invent an independent provenance identifier.

The validator's `Place` target metadata for Live raw-pointer leaves is likewise verification-only. It is the static counterpart needed to propagate defined RawAssign and RawMove path-state; it is not exposed by `ValidatedBody`, is not normative vocabulary, and does not add a provenance identity or access permission.

`ScalarType::TrackedFixture` and `Value::TrackedFixture` are synthetic non-copy fixture values with observable destruction solely to make ownership and destruction behavior testable. They are not Runen language scalar or value primitives.

`runen-reference::VerificationEvent`, `VerificationWriteKind`, and `ExecutionReport::verification_events` are verification instrumentation. Explicit borrow start/end, ordinary read, successful raw read/move, ordinary move, copy, ordinary/interior/raw write, `AddressOf`, raw-pointer move/copy, and fixture-drop records expose the reference machine's internal semantic transitions to tests; they are not the observable program trace defined by `spec/language/behavior.md`. Implicit forest termination at `Return` or `Fault` is not required to emit per-loan `BorrowEnd` verification events.

`runen-reference::UndefinedBehavior` and `UndefinedBehaviorKind` are likewise verification-only detection/reporting surfaces. They distinguish the concrete unsafe-precondition violations currently detectable by the oracle; their Rust variants are not normative Runen vocabulary, are not a complete UB taxonomy, and are not observable program outcomes.

## Oracle independence

The validator models the complete active loan forest explicitly, including parent/delegation state needed to prove ordinary MIR legality. It additionally models exact static raw-pointer targets solely because defined RawAssign and RawMove effects must update later path-state. When exact state proves a represented raw unsafe precondition fails, the validator may stop defined path-state propagation without emitting a MIR diagnostic or inventing post-UB state. It does not thereby discharge the unsafe obligation or make UB observable.

The reference machine stores only each active loan's concrete root and kind: the root resolves already-validated loan-relative accesses, while root plus kind are the minimum execution state needed to check RawRead shared target compatibility and RawMove/RawAssign exclusive target compatibility. The reference machine does not duplicate validator-owned parent-authority or reborrow-legality checking.

A raw pointer target is resolved by matching its symbolic dynamic `StorageInstanceId` to the current local storage instance and then applying its structural projection path. The oracle does not reinterpret the numeric identity as a `LocalId` or physical address.

Dynamic storage-instance verification identities, validator exact target places, and oracle raw-pointer targets are symbolic verification state derived from the accepted semantic model, not from native addresses or allocator identity. Host ownership, host references, host destruction, native addresses, allocator identity, container order, backend alias analysis, and host scheduling are not semantic oracles.
