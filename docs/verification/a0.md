# A0 Verification Contract

Status: **non-normative conformance-oracle documentation**

This document owns the test obligations for the executable A0 oracle. The normative semantics exercised by A0 are owned by `spec/language/core/value-storage.md`, `spec/language/core/borrowing.md`, and `spec/language/core/pointers.md`.

## Core MIR validation boundary

Raw `runen-core-ir::Body` is a construction/data form. It is not executable by the reference machine until `validate_body` establishes the structural and language-validity rules represented by the current A0 MIR and returns `ValidatedBody`. This is language validation, not the environment-admission phase defined by `spec/language/lifecycle.md`.

Validation rejects unknown identifiers and types, recursive by-value type graphs unsupported by the current structural representation, invalid block targets and direct/loan-relative place projections, operand/value type mismatch, `Copy` of a non-copy type, ordinary assignment to an immutable containing local, `InteriorAssign` whose resolved target is outside an interior-mutable region, and `AddressOf` whose destination raw-pointer pointee type does not match the selected source type. Raw-pointer pointee edges are semantic indirection rather than structural containment, so they do not make an otherwise finite structural type recursively invalid.

Validation also proves the current MIR's reachable initialization and active-loan-forest state transitions. `Init` requires Never-initialized storage; reads, moves, and copies require fully initialized storage; explicit `Drop` requires at least one Live subobject; every root borrow or reborrow requires a fully Live selected target and compatible current authority. `InteriorAssign` requires shared alias authority plus an independently marked interior-mutable target. `AddressOf` requires shared alias authority but does not require the selected stored value to be Live because it selects existing storage without reading the pointee value. Because the current A0 control-flow form has one successor per nonterminal block, validation follows the exact abstract path and terminates successfully when a `(block, storage state, active-loan-forest state)` tuple repeats.

The reference machine accepts only `ValidatedBody`. Its execution API therefore has no malformed-MIR or language-invalid-MIR result. A terminating execution produces `ExecutionReport`; cyclic valid MIR may diverge. A represented `Terminator::Fault` is a defined terminal execution, not a validation error, and performs the cleanup required by the normative value/storage semantics after the complete active loan forest ends.

## Lifetime and destruction-domain coverage

The oracle uses the normative distinction between storage extent and stored-value lifetime. Existing `NeverInitialized`, `Live`, and `Dead` state is sufficient for the current stored-value lifecycle; this verification layer does not invent stored-value lifetime IDs or numeric addresses.

Tests must distinguish at least these consequences:

- the same storage may remain in extent while successive stored-value lifetimes begin and end;
- move ends source stored-value lifetime without destruction;
- explicit destruction leaves Dead storage, so `Init` cannot treat it as fresh Never-initialized storage;
- mutable `Assign` may begin a new stored-value lifetime after move or destruction;
- ordinary and interior assignment evaluate their source before determining and destroying the destination's current destruction domain;
- interior replacement may occur without ordinary local assignment mutability when the destination is independently marked interior-mutable and the borrowing requirement is satisfied;
- explicit drop and termination cleanup destroy only the then-Live destruction domain and never repeat destruction of moved or already-destroyed leaves;
- defined `Fault` uses the same current-domain cleanup rule as defined `Return`.

Verification events expose enough ordering to prove these rules where the synthetic tracked fixture is used, but those events remain non-observable oracle instrumentation.

## Dynamic storage identity and raw-pointer formation coverage

The reference machine creates one verification representation of dynamic storage-instance identity for each local storage extent in an execution. That identity remains stable for the extent and is distinct from static `LocalId`, stored-value lifetime, pointer provenance, and physical or numeric address semantics.

`Operand::AddressOf` forms a non-null raw-pointer runtime value by selecting one symbolic `StorageRegion`: the target local's dynamic storage-instance identity plus its structural projection path. The currently defined provenance fact is only that the pointer's provenance is rooted in the target dynamic storage instance. The oracle therefore stores the symbolic target once; `target.instance` is sufficient verification evidence for that provenance root and is not a separately observable provenance token.

Validation and execution must prove at least:

- distinct simultaneously existing local storage extents receive distinct dynamic storage-instance identities;
- one continuing local storage extent keeps the same identity across initialization, move, explicit destruction, ordinary replacement, and interior replacement;
- structural projections in pointer targets are semantic paths rather than byte offsets or layout facts;
- direct and loan-relative `AddressOf` selecting the same concrete storage produce the same currently defined symbolic target/provenance-root metadata;
- pointer formation may select Never-initialized or Dead storage while its storage extent continues;
- ending or reusing the loan that authorized formation does not mutate an already formed raw-pointer value;
- ordinary raw-pointer `Copy`, `Move`, storage, replacement, and destruction preserve or consume the raw-pointer value according to ordinary value/storage rules while preserving its defined pointer metadata where the value continues.

Raw-pointer dereference/load/store, pointer arithmetic, numeric-address conversion, complete provenance structure or invalidation, relocation or pinning, pointer equality/ordering/hashing, null semantics, value validity, dangling access, and undefined-behavior closure remain outside this verification contract because their normative semantics are not defined by the accepted A0 slice.

## Borrow and access coverage

Borrow intervals are separate from storage extent and stored-value lifetime.

`Body::loans` declares typed semantic loan identities. A declaration may be activated for multiple sequential borrow intervals, but it cannot be activated twice concurrently. `Statement::Borrow` takes a `PlaceAccess`: a direct source creates a root interval, while an active-loan source creates a child interval. Each dynamic activation receives fresh concrete-root and parent state.

`PlaceAccess::Direct` reaches storage through its local place. `PlaceAccess::Loan` reaches an active loan root plus relative structural projections. Neither representation is a pointer value, physical address, provenance token, stored reference, or frozen source-language reference syntax.

Validation and execution must prove at least:

- place overlap is structural and address-independent: roots overlap descendants while sibling fields are disjoint;
- overlapping shared root loans may coexist;
- an exclusive root loan conflicts with every overlapping active loan;
- exclusivity and assignment mutability remain separate: immutable storage may participate in exclusive root borrowing and exclusive reborrowing while ordinary assignment remains illegal;
- shared loans permit `Read`, copyable `Copy`, `AddressOf`, shared reborrow creation, and `InteriorAssign` only when the independently resolved target lies within an interior-mutable region;
- shared loans do not permit `Move`, ordinary `Assign`, `Drop`, or exclusive reborrow;
- exclusive loans include shared authority and additionally permit `Move`, `Drop`, exclusive reborrow, and ordinary `Assign` when containing-local assignment mutability permits it;
- direct reads, copies, `AddressOf`, and legal `InteriorAssign` may coexist with overlapping shared loans, while direct exclusive-authority operations may not;
- any overlapping exclusive loan blocks direct shared or exclusive access;
- shared children may be created from shared or exclusive parents that retain shared authority;
- exclusive children may be created only from exclusive parents that retain exclusive authority;
- a child borrow delegates only its concrete overlapping region; disjoint parent sub-places retain their prior authority;
- an overlapping exclusive child completely suspends direct-parent access to that region;
- an overlapping shared child leaves shared authority on that region, including `Read`, copyable `Copy`, `AddressOf`, shared reborrow, and eligible `InteriorAssign`, while blocking exclusive-authority operations;
- only direct children are required to compute a parent's retained authority because deeper descendants cannot return authority to the grandparent while their direct ancestor remains active;
- explicit parent end is rejected while a child remains active, so nested intervals end leaf-to-root;
- ending a child restores the direct parent's prior authority subject to any other active direct children;
- active loan declarations form a forest and an active declaration cannot be reused to create a cycle;
- reusing an inactive `LoanId` creates a fresh interval without stale parentage;
- exclusive access controls storage rather than one stored-value lifetime, so move/drop followed by ordinary assignment through the same active exclusive root or child loan is legal for mutable storage when ordinary value/storage rules permit it;
- shared loans may remain active across legal interior replacement because the loan governs the continuing structural storage region rather than one immutable stored-value lifetime;
- active-loan forest state participates in loop-state repetition;
- defined `Return` and defined `Fault` end the complete active loan forest before cleanup.

Source lifetime parameters or inference, first-class reference values, source-level interior-mutability APIs or runtime borrow guards, raw-pointer memory access, complete provenance semantics, relocation or pinning, allocation/deallocation, value validity, undefined behavior, source `unsafe`, and concurrency/memory-ordering semantics remain outside this verification contract.

## Required cases

The A0 suite covers at least:

- move invalidates the source, with a later use rejected by MIR validation;
- copy preserves the source;
- partial move preserves disjoint live sub-places and makes the aggregate unreadable as a whole;
- independently initialized fields can form a fully initialized aggregate;
- non-copy values cannot be copied;
- `Init` cannot reinitialize Dead storage after move or explicit destruction;
- mutable `Assign` can initialize Never-initialized storage;
- mutable `Assign` can reinitialize Dead storage after move or explicit destruction;
- mutable `Assign` can replace partially initialized aggregate storage while destroying only live old subobjects;
- source-first ordinary assignment updates related storage state before the destination destruction domain is determined;
- immutable ordinary assignment is rejected;
- assignment destroys a live replacement target before writing the new value;
- explicit partial-aggregate drop destroys only live subobjects;
- moved or already-dropped values are not destroyed twice;
- field and local cleanup order matches the normative value/storage semantics;
- defined fault cleanup uses the then-current destruction domain and destroys each remaining live value exactly once;
- structural root/field overlap and sibling disjointness;
- overlapping shared root loans, conflicting exclusive root loans, and disjoint exclusive field loans;
- direct-versus-loan permission cases for shared and exclusive borrowing;
- shared child from shared parent and shared child from exclusive parent;
- exclusive child from exclusive parent and rejection from shared parent;
- exclusive-child parent suspension and shared-child parent downgrade;
- disjoint delegated child regions preserve parent authority;
- overlapping shared children and disjoint exclusive children;
- parent end with active descendants is rejected;
- child end restores parent authority;
- nested grandchild delegation composes recursively;
- child source must be fully Live;
- immutable storage can be reborrowed exclusively without gaining ordinary assignment permission;
- exclusive move/drop followed by replacement through the same root or child loan for mutable storage;
- reborrow-source projections are statically typed even when unreachable;
- sequential loan declaration reuse has fresh parentage;
- loan-tree cycles cannot be formed by reactivating an already-active declaration;
- termination cleanup with still-active root and nested loans;
- state-changing loops are checked across repeated iterations, while a repeated valid `(block, storage state, active-loan-forest state)` is recognized as possible divergence rather than a validation failure;
- `InteriorAssign` is rejected outside an interior-mutable region and does not inherit legality from ordinary local mutability;
- shared alias authority can perform eligible interior replacement without gaining ordinary assignment, drop, move, or exclusive-reborrow authority;
- an exclusive loan can perform eligible interior replacement because exclusive authority includes shared authority, while the interior-mutability marker remains independently required;
- interior replacement follows source-first destruction/replacement ordering, destroys only then-Live old contents, and remains correctly cleaned on defined fault;
- stable interior-assignment loops add no hidden validation state;
- distinct local storage extents have distinct pointer-provenance roots in the current storage-rooted model;
- field `AddressOf` records a structural target path without layout semantics;
- direct and loan-relative pointer formation agree on the underlying target storage region when they select the same storage;
- pointer formation before and after ordinary or interior replacement preserves the continuing storage identity and currently defined pointer metadata;
- move and explicit drop end stored-value lifetimes without changing the continuing target storage identity;
- raw-pointer copy and move preserve the defined symbolic pointer metadata;
- ending the source loan does not mutate a previously formed raw pointer;
- shared-child, exclusive-child, disjoint-child, inactive-loan, and Dead-storage cases enforce the accepted alias-authority rules for `AddressOf`.

## Semantic and verification-only constructs

`Statement::Read`, `Statement::Borrow`, `Statement::EndBorrow`, and `Statement::InteriorAssign` represent semantic Core operations in the current proving MIR. `Operand::AddressOf` represents the currently defined raw-pointer formation operation. `PlaceAccess` records whether an operation reaches storage directly or relative to an active loan. These MIR forms do not claim source-language syntax, runtime reference representation, or stored reference identity.

`StorageInstanceId` and `StorageRegion` are proving/oracle representations of the accepted dynamic storage identity and structural-region semantics. Their numeric identity representation and structural projection data are not physical addresses, byte offsets, ABI layout, or Runen-observable values.

`runen-reference::RawPointerValue` is the oracle's private runtime representation of one currently defined raw-pointer value. Its symbolic `target` is the single stored source of truth for the accepted pointer target and provenance root; the oracle does not invent an independent provenance identifier.

`ScalarType::TrackedFixture` and `Value::TrackedFixture` are synthetic non-copy fixture values with observable destruction solely to make ownership and destruction behavior testable. They are not Runen language scalar or value primitives.

`runen-reference::VerificationEvent`, `VerificationWriteKind`, and `ExecutionReport::verification_events` are verification instrumentation. Explicit borrow start/end, read, move, copy, ordinary/interior write, `AddressOf`, raw-pointer move/copy, and fixture-drop records expose the reference machine's internal semantic transitions to tests; they are not the observable program trace defined by `spec/language/behavior.md`. Implicit forest termination at `Return` or `Fault` is not required to emit per-loan `BorrowEnd` verification events.

## Oracle independence

The validator models the complete active loan forest explicitly. The reference machine stores only the concrete active-loan roots needed to execute already-validated loan-relative access; it need not duplicate permission checking or parent-authority validation.

Dynamic storage-instance verification identities and raw-pointer targets are symbolic oracle state derived from the accepted semantic model, not from native addresses or allocator identity. Host ownership, host references, host destruction, native addresses, allocator identity, container order, backend alias analysis, and host scheduling are not semantic oracles.
