# A0 Verification Contract

Status: **non-normative conformance-oracle documentation**

This document owns the test obligations for the executable A0 oracle. The normative semantics exercised by A0 are owned by `spec/language/core/value-storage.md` and `spec/language/core/borrowing.md`.

## Core MIR validation boundary

Raw `runen-core-ir::Body` is a construction/data form. It is not executable by the reference machine until `validate_body` establishes the structural and language-validity rules represented by the current A0 MIR and returns `ValidatedBody`. This is language validation, not the environment-admission phase defined by `spec/language/lifecycle.md`.

Validation rejects unknown identifiers and types, recursive by-value type graphs unsupported by the current representation, invalid block targets and direct/loan-relative place projections, operand/value type mismatch, `Copy` of a non-copy type, `Assign` through an immutable direct local, and exclusive root borrowing from an immutable containing local.

Validation also proves the current MIR's reachable initialization and root-loan state transitions. `Init` requires Never-initialized storage; reads, moves, and copies require fully initialized storage; explicit `Drop` requires at least one Live subobject; root borrowing requires a fully Live target and compatible active-loan state. Because the current A0 control-flow form has one successor per nonterminal block, validation follows the exact abstract path and terminates successfully when a `(block, storage state, active-loan state)` tuple repeats.

The reference machine accepts only `ValidatedBody`. Its execution API therefore has no malformed-MIR or language-invalid-MIR result. A terminating execution produces `ExecutionReport`; cyclic valid MIR may diverge. A represented `Terminator::Fault` is a defined terminal execution, not a validation error, and performs the cleanup required by the normative value/storage semantics after remaining root borrow intervals end.

## Lifetime and destruction-domain coverage

The oracle uses the normative distinction between storage extent and stored-value lifetime. Existing `NeverInitialized`, `Live`, and `Dead` state is sufficient for the current MIR: this verification layer does not invent stored-value lifetime IDs, addresses, or provenance tokens.

Tests must distinguish at least these consequences:

- the same storage may remain in extent while successive stored-value lifetimes begin and end;
- move ends source stored-value lifetime without destruction;
- explicit destruction leaves Dead storage, so `Init` cannot treat it as fresh Never-initialized storage;
- mutable `Assign` may begin a new stored-value lifetime after move or destruction;
- assignment evaluates its source before determining and destroying the destination's current destruction domain;
- explicit drop and termination cleanup destroy only the then-Live destruction domain and never repeat destruction of moved or already-destroyed leaves;
- defined `Fault` uses the same current-domain cleanup rule as defined `Return`.

Verification events expose enough ordering to prove these rules where the synthetic tracked fixture is used, but those events remain non-observable oracle instrumentation.

## Root-borrow and access coverage

The oracle also models root borrow intervals explicitly. Borrow intervals are separate from both storage extent and stored-value lifetime.

`Body::loans` declares typed semantic loan identities. `PlaceAccess::Direct` reaches storage through its local place; `PlaceAccess::Loan` reaches the active loan root plus relative structural projections. Neither representation is a pointer value, physical address, provenance token, or frozen source-language reference syntax.

Validation and execution must prove at least:

- place overlap is structural and address-independent: roots overlap descendants while sibling fields are disjoint;
- overlapping shared root loans may coexist;
- an exclusive root loan conflicts with every overlapping active loan;
- shared loans permit only non-consuming read/copy access in the current subset;
- exclusive loans permit read/copy/move/assign/drop subject to ordinary type, initialization, assignment, and destruction rules;
- direct reads/copies may coexist with overlapping shared loans but direct consuming/mutating operations may not;
- any overlapping exclusive loan blocks direct access;
- exclusive access controls storage rather than one stored-value lifetime, so move/drop followed by assignment through the same active exclusive loan is legal when the ordinary value/storage rules permit it;
- an explicitly ended loan cannot be used again until a new root borrow interval begins;
- loan identities may be reused after explicit end when the declared type matches the new target;
- active-loan state participates in loop-state repetition;
- defined `Return` and defined `Fault` end remaining root borrow intervals before cleanup.

Reborrowing, parent/child loan trees, interior mutability, source lifetime inference, first-class references, raw pointers, provenance, and pinning are outside this verification contract until their owning P0-A slices are accepted.

## Required cases

The A0 suite covers at least:

- move invalidates the source, with a later use rejected by MIR validation;
- copy preserves the source;
- partial move preserves disjoint live sub-places and makes the aggregate unreadable as a whole;
- independently initialized fields can form a fully initialized aggregate;
- non-copy values cannot be copied;
- `Init` cannot reinitialize Dead storage after move or explicit destruction;
- mutable `Assign` can initialize Never-initialized storage;
- mutable `Assign` can reinitialize Dead storage after move or explicit destruction;
- mutable `Assign` can replace partially initialized aggregate storage while destroying only live old subobjects;
- source-first assignment updates related storage state before the destination destruction domain is determined;
- immutable assignment is rejected;
- assignment destroys a live replacement target before writing the new value;
- explicit partial-aggregate drop destroys only live subobjects;
- moved or already-dropped values are not destroyed twice;
- field and local cleanup order matches the normative value/storage semantics;
- defined fault cleanup uses the then-current destruction domain and destroys each remaining live value exactly once;
- structural root/field overlap and sibling disjointness;
- overlapping shared loans, conflicting exclusive loans, and disjoint exclusive field loans;
- direct-versus-loan permission cases for shared and exclusive borrowing;
- exclusive move/drop followed by replacement through the same loan;
- explicit loan end, inactive-loan rejection, and legal loan reuse;
- termination cleanup with a still-active root loan;
- state-changing loops are checked across repeated iterations, while a repeated valid `(block, storage state, active-loan state)` is recognized as possible divergence rather than a validation failure.

## Semantic and verification-only constructs

`Statement::Read`, `Statement::Borrow`, and `Statement::EndBorrow` represent semantic Core operations in the current proving MIR. `PlaceAccess` records whether an operation uses direct access or an active loan. The current A0 kernel does not claim that these MIR forms are source-language syntax or runtime pointer representation.

`ScalarType::TrackedFixture` and `Value::TrackedFixture` are synthetic non-copy fixture values with observable destruction solely to make ownership and destruction behavior testable. They are not Runen language scalar or value primitives.

`runen-reference::VerificationEvent`, `VerificationWriteKind`, and `ExecutionReport::verification_events` are verification instrumentation. Borrow start/end, read, move, copy, write, and fixture-drop records expose the reference machine's internal semantic transitions to tests; they are not the observable program trace defined by `spec/language/behavior.md`.

## Oracle independence

The oracle must model Runen storage and loan state explicitly. Host ownership, host references, host destruction, native addresses, allocator identity, container order, backend alias analysis, and host scheduling are not semantic oracles.
