# Model Logical Data

Status: **provisional normative; incomplete**

This document owns the represented Model logical type/value foundation, explicit absence, closed structural records, finite logical collection values, and Model value equivalence. These semantics are independent of one physical storage, indexing, execution, serialization, or incremental-maintenance representation.

The represented `Bool`, fixed-width integer, and floating scalar member domains consume the accepted semantic value domains from [Core value and storage semantics](../core/value-storage.md), [Core integer semantics](../core/numerics/integers.md), and [Core floating-point semantics](../core/numerics/floating-point.md). The exact `F16`/`F32`/`F64` names below consume the already accepted mapping from those names to binary-floating format parameters in [Source type foundation](../source/types.md); that dependency supplies only the corresponding semantic member domains and does not import source type identity or source syntax into Model. This reuse is value-domain reuse only: Model logical type identity does not become Core per-program type-definition identity, Core storage identity, source declaration identity, or a physical representation guarantee. The Model-specific `Cardinality` scalar defined below does not consume a Core or source scalar member domain.

## Logical type algebra

The represented Model logical types are the least finite structural type expressions generated by the following forms:

- intrinsic logical scalars `Bool`, `I8`, `I16`, `I32`, `I64`, `U8`, `U16`, `U32`, `U64`, `F16`, `F32`, `F64`, and `Cardinality`;
- `Optional<T>` for a represented Model logical type `T`;
- one closed structural record type whose finite field-key map assigns one represented Model logical type to each field key;
- `Relation<T>` for a represented Model logical type `T`;
- `Bag<T>` for a represented Model logical type `T`; and
- `Sequence<T>` for a represented Model logical type `T`.

"Least finite" means every represented type expression has finite structure produced only by the constructors above. This revision defines no recursive nominal Model type declaration, hidden recursive schema identity, or unbounded type graph. `Cardinality` has an unbounded member domain, but it remains one atomic finite type-expression node; "least finite" constrains type-expression structure rather than the number of semantic members of a scalar domain.

No represented Model logical type in this revision is a safe reference, raw pointer, callable or closure value, Exec resource, state-domain handle, storage handle, target-sized integer, string, byte sequence, character, enum, variant, graph, field, or other opaque/resource-bearing category. Those require separately accepted owners and consumers.

## Logical type equality

Represented Model logical type equality is exact and structural over the type algebra above:

- two intrinsic logical scalar types are equal exactly when they are the same intrinsic identity;
- `Optional<A>` and `Optional<B>` are equal exactly when `A` and `B` are equal;
- two logical record types are equal exactly when they have the same field-key set and each shared key maps to equal logical types;
- `Relation<A>` and `Relation<B>` are equal exactly when `A` and `B` are equal;
- `Bag<A>` and `Bag<B>` are equal exactly when `A` and `B` are equal;
- `Sequence<A>` and `Sequence<B>` are equal exactly when `A` and `B` are equal; and
- types headed by different constructors or collection families are never equal merely because their values, storage, or realizations could look alike.

`Cardinality` is therefore not equal to `U64`, another fixed-width integer type, or any other intrinsic scalar merely because some of their members can denote the same mathematical non-negative integer.

Record field enumeration/declaration order is not a logical type-equality dimension. Source type identity, Core type-definition identity, physical layout compatibility, serialization compatibility, or implementation representation does not make two Model logical types equal.

## Intrinsic logical scalars

The represented intrinsic logical scalar member domains are:

- `Bool` has exactly `true` and `false`;
- each fixed-width integer type has the accepted mathematical value domain for that exact signedness and width;
- `F16`, `F32`, and `F64` have the accepted binary-floating semantic member domains selected by their exact accepted format parameters, including signed zero, signed infinity, and a non-empty NaN class; and
- `Cardinality` has exactly the non-negative finite mathematical integers `0, 1, 2, ...`, with no fixed maximum member.

`Cardinality` is an exact Model semantic domain for finite logical cardinalities. Its unbounded member domain does not define a target-sized integer, an arbitrary-precision source or Core integer type, a physical big-integer representation, arithmetic operators, an ordering/comparison relation, implicit conversions, literal or formatting syntax, or a serialization format. Any such consumer requires its own accepted contract.

A Model scalar type is not identified by a Core type-definition token, source type declaration, physical machine type, ABI type, byte encoding, or backend type. Sharing a semantic scalar member domain does not create cross-stratum type identity or an implicit conversion. `Cardinality` in particular has no corresponding Core or source type identity in this revision; a future crossing requires an explicit bridge/consumer contract.

## Explicit absence

For every represented Model logical type `T`, `Optional<T>` has exactly two tagged value forms:

- `Absent`; and
- `Present(v)` where `v` is one value of exact logical type `T`.

`Absent` is typed by its containing `Optional<T>`. It is not an untyped universal null and is not a member of non-optional `T`.

Absence is not record-field omission. A represented record value always contains one value for every field in its record type; an absent field value is represented only when that field's declared logical type is `Optional<T>` and its value is `Absent`.

Nested optionals remain distinct tagged structure. In particular, `Absent : Optional<Optional<T>>`, `Present(Absent) : Optional<Optional<T>>`, and `Present(Present(v)) : Optional<Optional<T>>` are distinct values before the equivalence relation below is applied, and that relation does not collapse those tag structures.

This revision defines no SQL `NULL`, three-valued predicate logic, truthiness, implicit absent propagation, coalescing/defaulting, absent ordering, aggregate treatment of absence, source spelling, or serialization of absence.

## Closed structural records

A represented Model logical **field key** is an abstract logical schema identifier with exact key equality. This revision does not derive field-key identity from source lexical spelling, source module/declaration identity, field position, physical column index, byte offset, storage key, or serialized name.

A represented logical record type is one finite map from pairwise-distinct field keys to represented Model logical types.

The logical type-equality relation above determines record type equality from field-key/type mappings. Enumeration, declaration, construction, storage, or presentation order is not a record-type identity dimension.

A value of one logical record type contains exactly one value of the declared logical type for every field key in that record type and contains no additional field. A record value has no hidden row, entity, source-declaration, allocation, address, or storage identity.

The empty field map therefore defines one represented empty logical record type, and its unique record value contains no fields.

Source nominal record declarations do not automatically establish Model record types, field keys, record values, or record identity. Any future source-to-Model mapping is an explicit bridge/consumer contract.

Field keys in this section are schema components only. They do not define the stable logical entity/key semantics that later Model state, join, reconciliation, or maintenance consumers may require.

## Finite collection values

The represented base collection families are:

```text
Relation<T>   finite unordered set
Bag<T>        finite unordered multiset
Sequence<T>   finite ordered sequence
```

where `T` is one represented Model logical type.

Collection membership and multiplicity use the canonical Model value-equivalence relation defined below.

A `Relation<T>` value is a finite set of `T` value-equivalence classes. It therefore contains at most one member per Model-equivalence class. Supplying or deriving two Model-equivalent candidate values cannot make two distinct Relation members; they denote the same member class.

A `Bag<T>` value is a finite map from `T` value-equivalence classes to positive finite multiplicities. Two Model-equivalent occurrences contribute to the same class multiplicity rather than becoming distinct identity-bearing members. A class absent from the bag has multiplicity zero and therefore need not appear in the finite map.

A `Sequence<T>` value has one finite length, one `T` value at each position, and one semantic finite linear order over those positions. Equivalent values at distinct sequence positions remain distinct occurrences because position and relative order are semantic for Sequence. This relation defines no numeric indexing base or source indexing syntax.

Empty Relation, Bag, and Sequence values are valid.

Relation and Bag expose no semantic iteration order. Storage order, hash order, index order, source order, worker order, scheduler order, or another physical traversal order cannot supply one. An operation whose result depends on one element being first requires Sequence input or a separately defined arbitrary-selection/ordering contract.

Sequence position and order are semantic. A realization MUST NOT manufacture or alter that order from incidental storage/index/scheduling facts.

For a concrete collection value, Relation size is the number of represented equivalence classes, Bag size is the sum of represented class multiplicities, and Sequence length is its number of positions. Each such concrete size or length is one non-negative finite mathematical integer and therefore belongs to the `Cardinality` member domain. These are concrete value facts only; they do not by themselves define a query operation that returns a `Cardinality` value or define static query-cardinality inference.

The exact Bag-cardinality aggregate and first exact Bag-to-Relation multiplicity-removal operation are owned by [Model queries](queries.md). This document supplies the collection, concrete-size, logical-type, and equivalence relations consumed by those operations; it does not own query execution semantics.

## Model value equivalence

Every represented Model value has exactly one represented Model logical type. **Model value equivalence** is one typed equivalence relation over represented Model values. It is the canonical relation consumed by Relation membership and Bag multiplicity and may be consumed by later Model operations only when their canonical owners explicitly do so.

Model value equivalence is not source `==`, SQL comparison, physical/bit equality, storage identity, pointer identity, hashing representation, serialization equality, query predicate semantics, ordering, or a general comparison API.

Values of different Model logical types are never Model-equivalent.

For values of the same exact logical type, equivalence is defined recursively as follows:

- `Bool`: two values are equivalent exactly when they are the same Boolean member;
- fixed-width integers: two values are equivalent exactly when they are the same mathematical member of that exact integer type;
- binary floating values other than NaN: two values are equivalent exactly when they are the same semantic member of that exact floating type;
- binary floating NaNs: every pair of NaN members of the same exact floating type is equivalent;
- `Cardinality`: two values are equivalent exactly when they are the same non-negative finite mathematical integer;
- `Optional<T>`: `Absent` is equivalent only to `Absent`; `Present(a)` is equivalent to `Present(b)` exactly when `a` and `b` are equivalent under `T`; `Absent` is never equivalent to `Present(v)`;
- records: two values of the same logical record type are equivalent exactly when, for every field key in that type, the two corresponding field values are equivalent under the field's declared logical type;
- `Relation<T>`: two values are equivalent exactly when they contain the same set of `T` equivalence classes;
- `Bag<T>`: two values are equivalent exactly when every `T` equivalence class has the same multiplicity in both bags; and
- `Sequence<T>`: two values are equivalent exactly when they have equal lengths and corresponding positions in their finite linear orders contain values equivalent under `T`.

The accepted floating semantics make `+0` and `-0` distinct semantic floating members. They are therefore **not** Model-equivalent in this revision. No host floating equality convention may merge them.

The accepted floating semantics deliberately leave NaN member identity underspecified while treating same-type NaN members as numerically equivalent for the accepted numeric contracts. Model therefore places all NaN members of one exact floating logical type in one Model-equivalence class. Otherwise permitted realization-specific NaN member choice could change Relation cardinality, Bag multiplicity classes, structural record equivalence, or maintained-result equivalence without any Model semantic input. This rule does not define source floating equality, hashing, total ordering, payload identity, sign identity, bit identity, or another operation-specific floating relation.

NaNs from different floating logical types are not equivalent because values of different Model logical types are never equivalent.

Because the relation is structural, physical row/column layout, field enumeration order, collection storage order, index shape, allocation identity, and worker schedule cannot change Model value equivalence.

## Cross-stratum and realization boundary

Model logical data is semantic data. A realization may use any storage, index, row/column organization, hash representation, encoding, or incremental structure that preserves the logical values and relations defined here. In particular, a realization of `Cardinality` may use any representation that preserves every required non-negative finite mathematical member; one finite machine integer carrier does not impose a semantic maximum or overflow behavior.

A Model logical value is not a Core storage place, storage instance, lexical borrow, reference authority, raw-pointer provenance object, source binding, or source declaration merely because a realization shares memory or because its scalar member belongs to a reused semantic scalar domain.

Model scalars, optionals, records, Relations, Bags, and Sequences do not automatically become Core values/aggregates or source types. Import, reification, observation, or conversion across a semantic stratum requires an explicit bridge/consumer contract. This includes `Cardinality`: its mathematical members do not create an implicit conversion to a fixed-width Core/source integer or require a source arbitrary-precision integer type.

## Deliberate boundaries

This document does not define stable logical entity keys or row identity, source Model syntax, query predicates or query execution relations beyond the data relationships explicitly delegated to [Model queries](queries.md), query-schema propagation, static cardinality/type inference, state-domain interfaces or revision ordering, multi-domain ObservationSet compatibility, materialization/freshness/maintenance target contracts, infinite or streaming collections, graph/path algebra, Datalog recursion, CRDT/replication semantics, distributed transactions, serialization/wire formats, physical row/column layout, indexes, planner behavior, or storage algorithms.

`Cardinality` does not by itself define arithmetic, comparison, ordering, conversion, formatting, parsing, serialization, source literal syntax, source/Core type identity, or a static-cardinality inference domain. Those require separate accepted consumers.

Graph and Field are not universal base Model data categories in this revision. Specialized graph, path, spatial-field, sampled-field, or similar algebras require separate accepted contracts rather than acquiring implicit semantics from Model.
